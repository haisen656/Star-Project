# QuickDrop 安全设计

## 机密与令牌

- 不存在用户注册、可见登录、密码、邮箱验证或长期账号资料。
- 匿名认证 JWT 只用于识别 RLS 主体；设备访问需要额外的 32-byte（至少 256-bit）随机令牌。
- 验证码、二维码 pairing token、设备令牌、IP 和设备指纹仅保存带 `PAIRING_HASH_SECRET` 的 hash。不要在数据库、日志、异常或分析系统写入明文。
- `PAIRING_HASH_SECRET`、`CRON_SECRET` 和 Supabase `service_role` 都只能设为 Edge Function secret，绝不能放入 `NEXT_PUBLIC_*`、`EXPO_PUBLIC_*`、移动包或网页脚本。

## 验证码和限流

- 验证码是展示便利性而非高熵秘密：它固定为 4 位，10 分钟有效，配对成功立即消费。
- 二维码令牌为 32-byte 随机值，防止只靠观察/枚举 4 位码进行二维码配对。
- 同一 IP 的创建空间、验证码尝试、上传操作均采用 15 分钟滑动窗口限流，默认最多 5 次。生产环境应让反向代理可信地传递 `cf-connecting-ip`/`x-forwarded-for`，并按流量接入 WAF。
- `pairing_codes.failed_attempts` 最多为 5，到达时将码作废；数据库函数串行消费同一配对码，并强制空间最多 3 台活跃手机。

## 文件与数据

- bucket 为私有，下载仅由 `get-download-url` 在完成设备/所有者鉴权后生成 60 秒 URL。
- 对外分享是明确的用户动作，而非公开 bucket：文件上传者或空间所有者生成的 32-byte 分享令牌默认存活一小时，数据库只保存 hash。二维码指向带令牌的下载页；服务端验证后才生成 60 秒 URL。生成新链接会使旧 token 失效。
- 上传签名函数检查单文件 2GB、空间总容量 2GB、文件名、扩展名、MIME 和危险可执行类型；文件名移除路径和控制字符。上传确认再次核对 Storage 元数据。
- 手机和网页只在用户点击后读取剪贴板。项目不实现后台剪贴板监听、录屏、后台文件扫描或后台读取。
- 局域网直传仅在手机 App 位于前台时工作；App 进入后台会中止未完成的直传并删除其临时字节，发送端自动回退到私有云端。浏览器直传文件限制为 64MB，避免接收端在用户保存前耗尽内存。
- 大文件本机直传使用可选的 Windows Bridge：每次传输令牌为 256-bit 随机值，仅以 hash 形式保留在进程内十分钟，绝不持久化或写入 Realtime。Bridge 不保存 Supabase key、设备令牌或配对凭证；手机只有在前台且收到空间私有 Realtime 消息后才会对持有该一次性令牌的 LAN 端点发起流式请求。详情见 `docs/local-bridge.md`。
- Android 为连接已配对电脑的专用 LAN HTTP 端点启用 cleartext traffic。应用层仅接受 RFC1918 私网 IPv4 端点、随机一次性令牌的本机 Bridge；公共 Wi-Fi 或不可信网络应让传输回退 HTTPS 私有 Storage。Windows 防火墙只允许 Bridge 使用“专用网络”，不要授予“公用网络”访问权。
- 所有删除动作走服务端，删除文件对象并软删除传输项；空间销毁和到期清理移除所有关联对象和数据库记录。

## 残余风险与部署建议

4 位码天生可猜，因此必须保留 IP 限流、短期有效、一次性消费，并建议通过 HTTPS、WAF 与 bot 防护部署。匿名身份也可能被滥用，应在生产环境为 Supabase Auth、Edge Function 与反向代理设置速率上限和监控。

签名 URL 在其 60 秒生命期内可被持有者使用；不要将它们记录到前端持久化存储。空间并非端到端加密：Supabase 运行方可在存储层访问文件。若需要端到端保密，应另行设计客户端加密、密钥交换和恢复模型。
